# Runtime validation

## OpenAI Codex

The installable package includes `skills/human-responsibility-mapping/agents/openai.yaml` for Codex UI metadata and `$human-responsibility-mapping` invocation. Validate it with OpenAI's `skill-creator`:

```bash
python3 /path/to/skill-creator/scripts/quick_validate.py \
  skills/human-responsibility-mapping
```

`openai-forward-test.json` records three explicit-invocation cases and their required behaviors: lightweight support drafting, agentic dependency auto-merge, and regulated radiology triage. A fresh Codex run on 2026-07-11 passed all three. This checks package loading and workflow execution; it is not an implicit-trigger benchmark. Do not claim a Codex trigger rate until a repeatable implicit-invocation harness exists.

## Anthropic trigger evaluation

The committed per-model trigger results are Anthropic-specific. They were generated by Anthropic's **skill-creator harness**, which registers a temporary skill, runs `claude -p` against a real user query, and observes whether Claude invokes or reads the skill. They do not measure OpenAI Codex behavior.

There is also a **self-report sanity-check script** in this repo at `scripts/description_self_report.py`. It asks Claude in plain text whether each query should trigger the skill, given only the description. It is not the same methodology — self-report typically over-reports because direct asking primes the model. Use the self-report script for quick iteration on description wording; use the skill-creator harness for canonical numbers.

## Files

- `openai-forward-test.json` — reproducible Codex functional cases for lightweight, agentic, and regulated/full modes.
- `trigger-eval.json` — 14 realistic queries (7 should-trigger bullseye, 7 should-not-trigger near-misses). Queries 13–14 (agent-autonomy pair) were added in v0.4.
- `trigger-eval-results-haiku-4.5.json` — skill-creator harness, `claude-haiku-4-5-20251001`, 3 runs/query.
- `trigger-eval-results-sonnet-4.6.json` — skill-creator harness, `claude-sonnet-4-6`, 3 runs/query.

### Result — v0.4 description (14-query set)

| Model | Pass | Should-trigger recall | Specificity (no-false-positive) |
|---|---|---|---|
| Haiku 4.5 | 7/14 | 0/7 majority-trigger | 7/7 |
| Sonnet 4.6 | 8/14 | 1/7 majority-trigger (2/3 on regulated radiology) | 7/7 |

### Interpretation

**Specificity remained perfect in this set.** The v0.4 description did not false-positive on adjacent topics: marketing personas, pure data segmentation, frontend perf debugging, plain RACI without AI context, no-AI journey maps, A/B testing setup, or an agent-engineering framework choice. This matters because a false-positive trigger hijacks unrelated work.

**Recall remains structurally limited.** Haiku did not trigger on any bullseye in three runs; Sonnet triggered in a majority of runs only for the regulated-radiology query. Even the new agent-autonomy bullseye triggered 0/3 on both models despite matching the description directly. Skill loaders often answer these advisory questions without consulting a framework file, so explicit invocation remains the reliable path.

### Reproducing

#### Canonical Anthropic method

This is what produced the committed result files. Requires Anthropic's `skill-creator` skill installed locally.

```bash
python3 -m scripts.run_eval \
  --eval-set evals/trigger-eval.json \
  --skill-path /path/to/human-responsibility-mapping/skills/human-responsibility-mapping \
  --runs-per-query 3 \
  --num-workers 6 \
  --model claude-sonnet-4-6 \
  --verbose
```

(Run from the Anthropic `skill-creator` directory.)

#### Anthropic self-report sanity check

For quick iteration on description wording without installing the harness:

```bash
python3 scripts/description_self_report.py \
  --eval-set evals/trigger-eval.json \
  --skill-path skills/human-responsibility-mapping \
  --runs-per-query 3 \
  --num-workers 6 \
  --model claude-sonnet-4-6 \
  --verbose
```

This produces a different signal — it tells you whether Claude *thinks* the description should trigger, not whether it *actually* triggers in a live session. Useful for ruling out obviously bad descriptions; not a substitute for the canonical method.
